# ShopSphere — E-Commerce & Inventory Management System

Full-stack MERN-style project: **React (Vite) + Tailwind** frontend, **Node/Express** REST API, **MongoDB/Mongoose**, **JWT** (access + refresh) auth with **RBAC**, **Socket.IO** real-time updates and an internal **EventEmitter** event bus. Three roles — **Customer, Seller, Admin** — each with their own permissions and UI.

> Payments are **simulated**. No real money moves anywhere; every payment object carries `simulated: true` and the UI/API say so.

## Quick start

**Prerequisites:** Node 18+ (tested on 22), MongoDB 6+ (local **replica set** or MongoDB Atlas).

### 1. MongoDB
Transactions (used at checkout/cancel) need a replica set. Easiest options:
- **Atlas (free tier)** — paste its connection string into `MONGO_URI`.
- **Local single-node replica set**
  ```bash
  mongod --dbpath ./data --replSet rs0
  # in another terminal (once):
  mongosh --eval 'rs.initiate({_id:"rs0",members:[{_id:0,host:"127.0.0.1:27017"}]})'
  ```
- **Plain standalone MongoDB** also works: set `USE_TRANSACTIONS=false` and the app falls back to atomic conditional updates + compensating rollbacks (same test suite passes in both modes).

### 2. Backend
```bash
cd backend
cp .env.example .env        # edit secrets + MONGO_URI
npm install
npm run seed                # sample users, categories, products, coupons, history
npm run dev                 # http://localhost:5000  (health: /api/health)
```

### 3. Frontend
```bash
cd frontend
npm install
npm run dev                 # http://localhost:5173  (proxies /api and /socket.io to :5000)
```

## Feature checklist
| Area | Implemented |
|---|---|
| Auth | Register (customer/seller), login, bcrypt (cost 12), JWT access (15m) + rotating refresh tokens (hashed in DB), logout, change password, profile |
| RBAC | `protect` + `authorize(roles)` middleware; sellers need admin approval; deactivated users blocked immediately |
| Catalog | Products CRUD with **seller ownership checks**, categories, search/filter/sort/pagination, soft delete |
| Cart | Server-calculated totals, stock caps, per-user isolation, coupon apply/remove |
| Orders | Atomic stock reservation, price/stock **revalidation**, price **snapshots**, valid status transitions, cancel + **stock restore exactly once** |
| Coupons | Percent/fixed, min order, max discount, start/expiry, global + per-user limits, atomic usage counter, restored on cancel |
| Payments | Simulated card/UPI/COD, success/failure outcomes, clear "SIMULATED" labelling |
| Inventory | Atomic add/remove/set (never negative), thresholds, low-stock list, valuation |
| Reviews | Verified buyers only (delivered orders), one per product, rating aggregate maintained |
| Wishlist, Notifications | Persisted + pushed live via Socket.IO |
| Real-time | `order:status`, `notification`, `inventory:changed`, admin `order:new`/`inventory:lowStock` |
| Events | EventEmitter: `order.placed`, `order.statusChanged`, `order.cancelled`, `inventory.changed`, `inventory.lowStock` |
| Analytics | Aggregation pipelines: summary KPIs, sales by date, revenue by category, best sellers, order status mix, inventory valuation (role-scoped) |
| Quality | zod validation (every body), central error handler, morgan + leveled logger, helmet, CORS, login rate limit, env-based config |

## Design decisions worth knowing
- **One status per order.** In a multi-seller order every involved seller sees *only their own line items*, but a status change applies to the whole order. (A per-seller fulfilment split is the natural next step.)
- **"Revenue"** counts line items of `confirmed/shipped/delivered` orders. Coupon discounts are order-level and are not allocated to sellers' line revenue.
- **Pending + simulated payment** orders cannot be confirmed until paid (COD can).
- **Refresh tokens** are returned in the JSON body and kept in `localStorage` for simplicity; production hardening would move them to httpOnly cookies.
- Product images are URLs (seed data uses picsum.photos). There is no file-upload module.

## Environment variables
See `backend/.env.example`. Secrets are never committed; the backend refuses to start if `MONGO_URI` or the JWT secrets are missing.
